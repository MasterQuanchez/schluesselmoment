Building software when agents do the typing.

The single guide to what this repo is about: a structured SDLC where capable coding agents handle most of the implementation, and humans stay accountable for intent and outcome.

What this repo is

An AI-first development template

A layered template: human intent on top, an orchestration layer that runs the loop, and the agent-factory SDLC underneath - with design, traceability, and security running across every stage.

Output quality is bottlenecked by your unknowns and your routing choices, not by the model - so the repo closes those gaps and keeps a human accountable, rather than trying to out-clever the model.

Orientation, not prophecy

The ends of the lifecycle matter more

One durable observation is enough: as agents absorb implementation, effort moves to forming intent and validating outcomes.

Matters less

  • Typing speed
  • Syntax recall and deep IDE mastery
  • Manual boilerplate
  • Line-by-line manual debugging

Matters more

  • Intent: framing, constraints, acceptance criteria
  • Validation: review and testing that scale
  • Orchestrating agents toward a clear goal
  • Architectural judgment and trade-offs

Treat this as a direction to lean into, not a fixed roadmap. The governance here (human checkpoints, specs, audit trails) holds regardless of the capability curve; the prompting technique adapts.

Core principles

How we work with agents today

1

AI augments, it does not replace

An over-confident, very fast pair programmer. Human leads, AI executes, verify everything - its failures are inhuman.

2

Context is king

Manage what the agent knows: AGENTS.md, rules, the right files. When a chat stops helping, reset context.

3

Capability amplifies expertise

Prompts inherit your judgment. Domain knowledge, not tricks, makes output good.

4

Hand a goal, not steps

Every dictated step overrides the agent's judgment with yours. Give the reason and the bar; let it find the path.

5

The builder never grades its own work

Whatever builds a thing is biased toward its own trajectory. Verify in a fresh context against the real output.

6

Humans stay accountable at the boundaries

Irreversible or external actions are gated or pre-authorized once, never silently automated.

The workflow

Two entry points, one language

Mix them: prototype Solo, formalize with the factory.

Solo is Cursor's native loop for fast, low-ceremony iteration - good for prototypes and experiments. Team (agent-factory) is the structured SDLC: work-item tracking, human checkpoints, and traceability, entered at any point. The spec (knowledge/specs/) is the durable contract across sessions; stages append to Implementation Notes.

Inner loop order is deliberate: test precedes review so the fresh-context reviewer consumes tester artifacts. When the plan or diff hits security surfaces, review runs Lane A (generic) then selective Lane B (Secure SDL).

The orchestration layer

Your role in prompting

You do not have to be a prompt engineer. The orchestrate skill runs the loop and shaping sequence; your job is narrower - supply what only you know, and approve before it runs.

The skill does the shaping

Using orchestrate, the agent locates the stage and its role, drafts the four components (context, request, output format, constraints), routes the model (naming it explicitly on spawn), and sets up the fresh-context verifier - the mechanical parts of a good prompt.

You supply what only you know

Give your starting point and known unknowns. Answer the grill (architecture-first, one question at a time). Confirm the hard bar for done. Approve the prompt and model before the run starts.

Durable core: the human always owns three things - close your unknowns, set a hard bar, name a fresh verifier. These survive any model generation because they encode your knowledge gaps and the org's trust boundary, not model-capability crutches. Expect the mechanical shaping to shrink as models improve; your three stay.

How it fires in practice

Three ways it engages

There is no silent prompt-rewriter. Cursor loads a skill when your message matches its description, then the agent follows it. What changes across the three modes is how much of the shaping the agent does for you, least to most automated.

Mode 1 - direct stage command

A plain command runs the stage; its inline pointer makes the agent apply the principles while executing. Your sentence isn't transformed.

implement T2 from the plan

Mode 2 - meta prompting

The agent helps you write the prompt: it runs the shaping pass, may grill you one question at a time, and hands back a launch prompt to approve.

help me prompt this: <idea>,
then show me the launch
prompt before running

Mode 3 - orchestration

The orchestrator writes each subagent's spawn prompt and routes its role to a model. The transformation is real, done by the agent.

orchestrate F001 end-to-end
as subagents

Orchestrating a run

From a shaped prompt to an autonomous run

Mode 2 is the natural way to draft a Mode 3 run: use meta prompting to write the orchestrator launch prompt, review it, then hand it to an orchestrator (ideally a cloud agent) to execute.

Separation of concerns

The value of this split is that alignment, implementation, and verification are done by different actors, at different times:

1

Align - you (Mode 2)

The discover grill happens here: you define the intent and what "done" means. The output is the spec - the contract the run is held to.

2

Implement - the agent (Mode 3)

A plan → implement → test → review inner loop runs autonomously against that spec. In HOTL the orchestrator approves the plan on the human's behalf.

3

Verify - a fresh-context subagent

Review runs in isolated context against the original spec. A separate subagent in the same session is enough - the builder never grades its own work.

So the human owns the two ends - intent at the start, acceptance at the finish - while the middle runs on its own. In HITL that human touch also lands between every stage; in HOTL it is front-loaded in the Mode 2 grill and repeated only at the end.

You ask for the prompt in plain language:

help me shape an orchestrator launch prompt to run F001-dashboard-api
end-to-end, human-on-the-loop, then show it to me before I run it

Mode 2 shapes it → you review and approve the prompt → Mode 3 executes it.

On your behalf, orchestrate runs the discover alignment - grilling you on the architecture-shaping unknowns once up front and pinning down what "done" means - then writes the four components, sets the gates, and routes each subagent's role to a model. Because alignment is already captured in the spec, the run itself only needs the plan → implement → test → review inner loop. The result is a launch prompt like this, which you approve before it runs:

orchestrate F001-dashboard-api end-to-end, human-on-the-loop.

Context: real-time analytics dashboard. Intent and acceptance criteria are already
  aligned in the spec at knowledge/specs/F001-dashboard-api.md (from the Mode 2 grill).
Goal (not steps): ship the feature to a reviewable PR - you decide the approach.
Inner loop: plan -> implement -> test -> review, each a subagent with role+model per models.toml.
House rules: follow existing codebase patterns; no new deps beyond the plan.
Bar for done: all acceptance criteria pass under a FRESH-context verifier subagent,
  verified by running the app end-to-end in your environment - not just a passing compile.
Pre-authorized actions: create the branch and commits; STOP before opening the PR or
  touching ADO - I approve those.
Log decisions and deviations to the spec's Implementation Notes as you go.
Report back with evidence (e2e results + the verifier's verdict).

Who verifies, and when

That approval step is a lightweight gate. The difference between the two modes is where the human sits: gating every stage, or verifying once at the end.

HITL - in the loop (default)

  • Human gates every stage
  • Plan approval, review verdict, test sign-off
  • Safe, cheap, no drift
  • The right default

HOTL - on the loop

  • One orchestrator session drives the stages
  • Human verifies once, at the end
  • Shines with cloud agents that test e2e in a VM
  • You get an already-exercised branch

Guardrails that stay even in HOTL

Fresh verifier

Review runs in a fresh-context subagent (different from the builder) pointed at the real output. Same session is fine.

Bounded actions

Git push, PR, and ADO items are gated or pre-authorized once, up front - never left fully open.

Durable spec

The orchestrator supervises drift via Implementation Notes on the spec; every deviation is auditable and syncs to ADO.

After the run: the reflect stage appends learnings to the spec and proposes harness improvements as a plan. The human decides what to act on - agents do not scatter state files.

Guidelines by role

What good looks like

Managers

Set expectations (review stays essential); enable the team via current AGENTS.md (dev rules and model-selection rubric); require tests and review for all AI code.

Designers & PMs

Prototype to think: have the agent generate several divergent directions as artifacts you react to, using the design skill and the WP toolkit. Front the intent - frame the problem, constraints, and acceptance criteria - so agents build the right thing.

Developers

Plan before building; prompt authoritatively with patterns and signatures; verify relentlessly (prefer integration tests); treat Git as the source of truth.

QA

Probe edge cases and regressions in untouched files; verify automated → acceptance → UI → security; watch for surprise dependencies and scope creep.

Testing AI-native (non-deterministic) features

LLM-backed features vary run to run, so exact-match assertions break. Use semantic checks (meaning and bounds), LLM-as-judge (score against input, gate on a threshold), human evaluation on a sample, and golden datasets to catch quality drift across model versions.

Safety and compliance

Guardrails around the agent

Three complementary layers - runtime hooks, data safety, and the Secure SDL harness. Do not collapse them.

Hooks

Block catastrophic operations, require confirmation for risky ones, prevent credential exposure, and audit actions. See docs/security.md.

Data safety

.sensitive/ is a gitignored vault; first names only in tracked files; secrets in .env. Say "check data safety".

Your responsibility

Review all AI code before merge, test security paths, never paste secrets into prompts, verify external calls.

Secure SDL harness (vendored copy)

Corporate Secure SDL leaves originate in Oscar's sdlskills repo. Their Cursor compiler installs them as always-on .mdc rules - the wrong fit here, where agent-factory already carries a large skill set.

Vendored as-is, not always-on

Keep leaf SKILL.md files under .cursor/skills/secure-coding/<leaf>/ and consume them as-is. Do not edit leaves to adapt them - interpretation lives only in agent-factory's Secure SDL leaf map. Refresh from upstream when Oscar ships changes; update the map if names or surfaces moved.

Selective, not the full pillar

plan / implement / test open only the leaves the surface cues imply (typically 1–few). Review is one stage, two lanes: Lane A generic (no leaf load); Lane B Secure SDL with control IDs and domain PASS/FAIL for loaded leaves. Auto-dispatch selective Lane B when the plan or diff hits security surfaces. Full-pillar breadth only on explicit ask.

Triggers: secure review, security review, or a normal review on a security-relevant change. Security is baked into HITL/HOTL stages - not a separate periodic product outside agent-factory.

Shape the intent. Validate the outcome. Keep the human accountable.
